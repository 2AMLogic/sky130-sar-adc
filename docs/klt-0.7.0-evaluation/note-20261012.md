# klayout-tools 0.7.0 evaluation against the pinned 0.6.0 (issue #649)

Dated 2026-10-12. Read-only evaluation: no pin, spec, or existing record was
changed. All runs used throwaway `uvx --from "klayout-tools==X"` environments
(klayout 0.30.12 for DRC); single-unit runs only.

## Decision

**No bump now.** Recorded reasons, each tied to a result below:

1. The 0.7.0 deck is a different deck (`released: true`, content hash
   `sha256:f8f2c3f4...`, versus the cited record's `sha256:a1d90e06...`) and
   on the composed top-level stream cited by item 3 it reports `violations`
   (32726), not `clean`. A layout-flow bump would therefore need a DRC triage
   first; this note does not do that triage.
2. The grader alone does not change any verdict (next section), so a
   grader-only bump to `signoff/requirements.txt` buys no verdict change. It
   would still force a re-render of `signoff/t1-report.json` (ruleset id and
   `source_doc_content_hash` change) and does not unlock item 6 (below).
3. The `[yield]` extra still does not resolve on 2026-10-12:
   `uvx --from "klayout-tools[yield]==0.7.0"` fails with
   "klt-yield-native was not found in the package registry" (upstream
   2AMLogic/klayout-tools#2900, already cited in `signoff/README.md`).

Revisit when: the `via3.width.1` findings below are triaged, and/or the
`klt-yield-native` wheel is published.

## 1. Grader: `klt signoff --manifest signoff/block-manifest.json`, 0.6.0 vs 0.7.0

Files: `grade-klt-0.6.0.json`, `grade-klt-0.7.0.json`, `grader-0.{6,7}.0.txt`
(`--describe-grader` output). Same manifest, same repo tree, only the klt
version differs.

- Control: the 0.6.0 re-grade `items` array is identical to the committed
  `signoff/t1-report.json` `items` (22 gradeable rows + 3 `tier_not_supported`
  rows; 4 met).
- 0.7.0: **all 25 item entries have the same `status` and `reason`** as 0.6.0
  (4 met: items 3 and 8 on both partitions; items 4 and 11 `check_failed`; the
  rest `no_evidence`). `t1_item_count` 22 and `t1_met_count` 4 unchanged.
  No row appears, splits, or disappears.
- Changed fields, all descriptive text only:
  - `text` of item 6 analog: adds the `undersized_sample` /
    `negative_control_not_detected` grading inputs for yield campaigns
    (issue #2467 upstream).
  - `text` of item 8 analog: restates which opt-in evidence kinds are bare vs
    artifact-anchored (pointer to `klt signoff --describe-grader`).
  - `text` and `notes` of item 11 analog, `notes` of item 11 digital: ERC
    supply-spec additions (`nets[].islands`, `same_net_as`,
    `unlabelled_allowed_boxes`, disclosed partial `ties[]` declarations), and
    the statement that item 11's LVS half is gated on item 4 passing.
- Provenance/schema: `schema_version` stays 1; `build.version` 0.7.0
  (git 0e2362b, v0.7.0, not dirty); `grading_ruleset_id`
  `sha256:0d8cc27c...` -> `sha256:eb8d2ba5...`; `source_doc_content_hash`
  `sha256:63eeec72...` -> `sha256:4c67ffc5...` (the checklist document bundled
  with the grader changed). Consequence: `run-signoff.sh --check` would fail on
  a 0.7.0 grader until the report is re-rendered, even though verdicts match.
- Not shown by this comparison: the grader consumes the cited records and does
  not re-run DRC, so item 3 stays `met` on the 0.7.0 grader because the cited
  `drc.json` was produced by the older build. The DRC section is the part
  that exercises 0.7.0's own judgement.

Observations on the 0.7.0 run over the item-3 stream (32726):
- 32716 are `*.ongrid.1` ("vertices must be on the 0.005 um manufacturing
  grid") across 19 layer rules, all zero-extent point markers; 10 are
  `via3.width.1`. The ongrid rule family (and `*.angle.1`) is new relative to
  the cited 0.6.0 record: `rules_checked` goes 52 -> 96 and `deck_layers`
  17 -> 40.
- By top-level source path (ongrid and width findings together), 31728 sit
  under `sar_sequencer__sar_sequencer` (largest ongrid contributors by source
  cell: `sky130_fd_sc_hd__dfrtp_1` 14952, `VIA_M1M2_PR` 3374,
  `sky130_fd_sc_hd__mux2_1` 3222), 830 under `halflsb_offset`, 160 under the
  `route` cell, 4 under `sampling_frontend`, 4 in the decap cells.
- The same ongrid rules report **0** violations on the later
  `20261003-041400-571f036` stream. This note did not investigate why the two
  streams differ; the later record's own cited `drc.json` was produced by a
  dev-head build whose deck already had the 96-rule coverage and reported 0.
- `via3.width.1`: 10 on both streams (per the rule description, via3 is "fixed
  0.2um"; the flagged boxes are 0.22 x 0.22 um, on `cap_array` instances
  inside CBOOT, CSAMP, CHOFF and the four decap units). On the later stream
  that makes 0.7.0 differ from the cited dev-head run (0 vs 10) with an
  identical `rules_checked` list but a different deck hash; this note does not
  establish whether that is a deck change, a rule-semantics change, or a
  genuine drawn-size finding. A comparison of the two decks' `via3.width.1`
  definitions is the first triage step.
- Provenance change: 0.7.0 reports `klayout_version_mismatch: false` and deck
  `released: true`; the cited 0.6.0 record has `klayout_version_mismatch: true`
  and `released: false`. Envelope `schema_version` is 2 in both; no new
  top-level keys.

## Storage

The full 0.7.0 envelope for the first stream is 16.6 MB (32726 violation
entries). It is not committed. `drc-klt-0.7.0.summary.json` is that envelope
with only `violations[]` emptied and a `_trimmed` block recording the omitted
entry count and the full file's sha256
(`258a194cd90eeae49b7dfd2666a12f8724712024f0f808c2a7b6bcfab27e9cc0`). It is expected to regenerate from the
commands below (the 0.6.0 run was byte-identical on re-run, which supports but
does not prove 0.7.0 determinism).

## Re-run check and an uncontrolled difference

A re-run of the `klt drc` command below on the LATEST stream, at the end of
this evaluation, matched the stored `drc-klt-0.7.0.superseding-gds.json`
(status, 10 violations, deck hash) byte-for-byte except
`provenance.klt_version`, which read `0.7.0+gb770c86e0e96` instead of `0.7.0`.
At that time `uvx --from "klayout-tools==0.7.0" klt --version` also printed
`klt 0.7.0+gb770c86e0e96` while `importlib.metadata` reported `0.7.0`; the
grade file from the earlier run records `build.git_commit` `0e2362b`
(`v0.7.0`). The two sessions therefore did not necessarily run an identical
0.7.0 build; this was not investigated, and the verdict comparison in section
1 and the DRC counts above are from the earlier-session files.

## Cold-start

```
# from the repo root; `klt signoff` exits non-zero for a block below T1, so capture stdout regardless
uvx --from "klayout-tools==0.7.0" klt signoff --manifest signoff/block-manifest.json --format json > grade-klt-0.7.0.json
uvx --from "klayout-tools==0.7.0" klt signoff --describe-grader
uvx --from "klayout-tools==0.7.0" klt drc layout/sar-adc-top/reports/20261001-211249-1ca34e6/sar_adc_top.gds --deck sky130 --format json > drc-klt-0.7.0.json
```

Same with `==0.6.0` for the control runs. The invocations are written from
`run-signoff.sh` and `klt drc --help`; the earlier builder run's exact command
lines were not preserved, so the `klt drc` form (stdout capture, `--deck
sky130`) is an unverified reconstruction until re-run.
