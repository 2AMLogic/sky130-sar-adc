# Pinned klayout-tools (`klt`) install for layout/'s DRC/LVS flow (issue #2).
#
# klt v0.2.0 on PyPI (https://pypi.org/project/klayout-tools) ships the
# gen/drc/extract/lvs/draw verbs this flow needs -- unlike
# 2AMLogic/sky130-bandgap's requirements.txt at the time it was written
# (issue #14 there), which had to pin a git commit because those verbs
# were only on `main`. Pinning the PyPI release here instead of a git SHA
# is simpler and reproducible the same way: an exact version, not a
# floating one.
#
# Provenance: pattern (pin-and-document-why, `--force-reinstall` discipline
# in layout/bin/setup-venv.sh) ported from 2AMLogic/sky130-bandgap's
# layout/requirements.txt (commit 1f04e8524cc2d8c2c7154773749b1b2d3be2ce64),
# per CLAUDE.md's "Harness bootstrap" instruction.

# Bumped 0.2.0 -> 0.3.0 for issue #101 (comparator sub-block layout): `klt
# gen-compose`'s 0.2.0 build only routes strictly 2-pin connectivity[] nets
# (a 3+-pin net -- e.g. this block's VDD/GND/OUTP/OUTN rails, each touching
# 3-8 device terminals -- comes back in unrouted_nets[] with no metal drawn).
# 0.3.0 adds bundle (>2-pin) routing as a spanning tree of two-pin legs
# (2AMLogic/klayout-tools#1094/#1073), which the comparator's own supply/
# output rails need directly -- not a hand-authored-netlist need, a real gap
# hit doing this sub-block's layout. No klt gap filed for this one: the
# capability already exists in a released version newer than the prior pin,
# so it is a pin bump, not a tool-tracker friction report.
#
# Independently required by issue #100 (CDAC array layout): 0.2.0's sky130
# extraction deck stops its metals/vias connectivity at met1, so a MiM-cap
# array with bottom plates on met3 and top-plate rails on met4 is not
# extractable on that pin at all. 0.3.0's met2-met5/via2-via4 connectivity
# is what makes the array's `klt extract`/`klt lvs` verdicts possible.
#
# One non-additive consequence of that bump, found re-running the six-verdict
# trivial-cell proof against it (issue #104): 0.3.0 also carries the
# dummy-device-suppression fix (klayout-tools#491/#494) that 0.2.0 predated.
# `klt extract --deck sky130` on `klt gen mos_array`'s defaults now reports
# device_count=4, dummy_devices_dropped=4 where 0.2.0 reported
# device_count=8, dummy_devices_dropped=0 -- so the three trivial-cell LVS
# reference netlists were re-derived from 8 M-cards to 4 in the same PR (see
# layout/trivial-cell/reference.spice's header, which forward-referenced
# exactly this fix). Bump the pin and re-run the proof together; a pin bump
# alone can silently invalidate the flow's own gating evidence.
#
# Bumped 0.3.0 -> 0.4.0 for issue #102 (SAR logic/sequencer layout): PR #105
# (place-and-route via `klt place-and-route`/OpenROAD) reached DRC-clean but
# hit an `klt extract`/`klt lvs` integration gap on the routed, DEF-merged
# GDS -- `--top-cell-pins` cannot distinguish a genuine top-level port from
# an internal DEF NETS connection point once the whole design is flattened
# into the top cell, so `klt lvs` had no reliable pin anchor and reported a
# full mismatch despite an exact (760=760) device-count match. Filed
# generically at 2AMLogic/klayout-tools#1385. 0.4.0 (first PyPI release
# after 0.3.0) ships both fixes: klt#1391 (surfaces a `warnings[]` entry
# when pin promotion produces zero usable top-level pins) and klt#1397/#1390
# (`klt extract --def-pins <def_path>`, which derives the declared
# top-level pin set directly from the routed DEF's own `PINS` section
# instead of guessing from GDS label nesting). `--def-pins` is what
# layout/sar-sequencer/bin/run-flow.sh now uses to reach a clean LVS
# verdict -- see that sub-block's README.md for the re-run writeup.
#
# Independently required by issue #99 (the full sampling front end sub-block
# layout), which reached the same 0.3.0 -> 0.4.0 bump on its own branch,
# concurrently and for entirely different reasons. #102's block above landed
# the pin move on `main` first; this block is kept alongside it rather than
# folded into it, because the two rationales are independent evidence for the
# same pin -- same convention as the #101/#100 pair for the 0.2.0 -> 0.3.0
# bump above. Two reasons, both hit directly building that layout:
#
#   1. MiM top-plate connectivity (the blocking one). `klt extract`'s
#      capacitor top-plate-via exclusion -- the rule that stops a MiM cap's
#      own via, which the DRM *requires* to overlap the bottom plate, from
#      reading as a short between the two plates -- was scoped on the 0.3.0
#      pin to the capacitor's `bottom_plate` layer in full, i.e. to EVERY
#      met3 shape drawn anywhere in the layout. Since a legal via3 is
#      enclosed by met3 by construction, that removed every via3 in the
#      design from the deck's generic met3<->met4 connectivity as soon as any
#      `capm` was drawn. A MiM cap's top plate therefore could not be routed
#      down to met2/met1 at all: all four of this sub-block's cap top plates
#      extracted as isolated single-terminal nets, and LVS could not match.
#      0.4.0 narrows the exclusion to `bottom_region.interacting(top_region)`
#      -- met3 that actually touches a `capm` plate -- which is the fix.
#      Verified directly: same GDS, 0.3.0 extracts 21 nets with four
#      single-terminal cap plates, 0.4.0 extracts 17 nets with none.
#
#   2. n-well DRC rules (klayout-tools#1420). 0.3.0's curated sky130 rule
#      table carried NO rules on layer 64 at all, so a deliberately-split
#      n-well -- which is exactly what DR-004/DR-007's body-tie domains are --
#      passed DRC vacuously on the rules that govern the split. That is why
#      layout/sampling-frontend-wells/ (issue #122) had to hand-transcribe
#      `drc/nwell_isolation.drc` and run it through `klt drc --engine klayout
#      --deck-file`. 0.4.0 adds `nwell.width.1`/`nwell.space.1` to the curated
#      deck, so layout/sampling-frontend/'s flow checks the well split with
#      the same deck it checks everything else with, needs no `klayout`
#      binary, and takes ~4 s.
#

#     reference change needed (unlike the 0.2.0 -> 0.3.0 bump).
#   - layout/comparator/bin/run-flow.sh    -- all six verdicts PASS.
#   - layout/sampling-frontend/bin/run-flow.sh -- the new flow, all eleven.

#     stamps) included. Pre-existing, and almost certainly the known
#     nondeterminism in KLayout's combine_devices() rather than a pin

#   - layout/sampling-frontend-wells/ (#149) -- needs a working `klayout`
#     binary for its `--engine klayout` stages; the binary in this environment

#     (Since landed on `main` as PR #155, which retired that flow's
#     hand-written drc/nwell_isolation.drc deck and inverted verdict 5 --
#     exactly the outcome anticipated here, measured against klt 0.4.0.)

# `klayout` itself was left unpinned here until issue #148: `klayout-tools`
# declares it as a dependency but does not pin an exact version, so `pip
# install` resolved whatever was newest on the day of the install (0.30.11
# in August 2026, 0.30.12 by September). Every DRC/extract/LVS verdict in
# `layout/` depends on this package (it is what actually implements
# KLayout's native `NetlistComparer`/`DeviceExtractor*`/DRC engine that
# `klayout_tools` wraps), so leaving it unpinned meant a verdict recorded on
# one day was not reproducible-by-construction on another -- exactly the gap
# issue #148's investigation had to rule out (by hand, across a four-cell
# version matrix) before it could conclude the root cause was elsewhere.
# Pinned to the version resolved when that issue's fix was verified, so the
# whole evidence chain (`klt` + the KLayout engine it wraps) is pinned, not
# just half of it.
klayout==0.30.12
